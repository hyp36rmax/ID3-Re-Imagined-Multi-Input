# Controller Menu Foundation — functional single-controller baseline

The separate **WHEEL** category contains Quick Setup, Overview, Bind Controls, Test Controls and Force Feedback. All five pages call existing game services. **CONTROLS** retains the familiar Controller & Keyboard table. Both categories edit one shared draft using the existing binding/evaluation system. WHEEL also exposes the experimental multi-input mode added by the sample foundation; neither category claims persistent physical identity support.

## Player workflow

1. Open Options → WHEEL. The device row identifies the selected device; the status line identifies the actual active device and any temporary fallback. Changing the device is now a preview until Save Changes. Keyboard bindings remain available.
2. **Quick Setup:** choose New Wheel Setup. This checkpoints the prior draft and selects separate versioned multi-input assignments, preserving original controller mappings. This sample disables FFB in that mode. The five stages are Steering, Accelerator, Brake, Shift up and Shift down. Steering has sequential left and right capture prompts; accept each direction before proceeding. Optionally capture shift up/down or keep each existing shift assignment. Release controls between captures. Review Steering together (left/right), then pedals and shifts before Save Changes. Cancel restores the draft that existed before Setup began; leaving an unfinished Setup or changing device also cancels Setup. A completed review stays pending across WHEEL pages. After a failed save, page changes keep the checkpoint and edits; Cancel Setup still explicitly restores the earlier draft until bindings have saved. No file is written until Save Changes.
3. **Overview:** toggle between saved and draft assignments. Controller assignments and all three keyboard slots are visible. Available Devices shows actual discovery status, including disconnected choices, with wrapped full names and a scrolling list. Selected, active and FFB output names have horizontal scroll areas for long names; use the adjacent change/arrows controls to select devices. Discovery strings are preserved, not reinterpreted as hardware claims.
4. **Bind Controls:** choose an action and controller/keyboard slot, then Rebind or Clear. Capture uses the existing armed/release/timeout logic. An occupied controller control is rejected with the conflicting action's name; it no longer swaps another action. Clear the named assignment explicitly, then rebind. Keyboard conflicts and reserved recovery keys retain existing validation. Clearing a disconnected controller's saved binding is allowed; capturing requires an active controller.
5. **Test Controls:** Start Live Test and exercise bindings. The page shows evaluated draft steering/pedal demand and ten action states. It uses the same binding evaluator as gameplay, before native steering response, deadzone and smoothing, which are unchanged. It does not read raw hardware again or display the packet that the menu has neutralized. Focus loss and capture suppression are labelled unavailable/guarded rather than presented as a successful zero-value test. The existing reconnect guard can suppress controller actions while keyboard recovery remains active. Physical Escape stops the test; page buttons also leave it. Held tested inputs must release before they can navigate the menu afterward; Escape remains available if a device cannot return to rest.
6. **Force Feedback:** edit enable, output selection, strength and inversion. Save Changes saves bindings, selected input device and these four settings, retaining unrelated unsaved option edits. Output discovery and existing runtime stop/ownership/focus protections are reused. The page contains no force test and does not need motor output.

**Save Changes** has identical behavior on CONTROLS and all five WHEEL pages. It saves bindings, then selected input device, then FFB settings through the existing persistence services. It does not apply unrelated audio, graphics or other option drafts. This is an ordered save across separate files, not an atomic transaction. If any step fails, saving stops: the message identifies what saved, what failed and what was not attempted. All remaining edits stay pending; retry Save Changes or explicitly choose **Discard Changes**. The status area scrolls for long errors. Leaving Controller/options or closing the menu is blocked after an incomplete save until retry succeeds or Discard Changes is chosen. Controller pages remain accessible. Application shutdown cannot preserve in-memory drafts.

Discard Changes restores the last successfully saved bindings, selected device and FFB settings while preserving unrelated option drafts; it cannot undo parts already persisted. A Setup checkpoint is retired as soon as bindings save, even if a later step fails, so Cancel cannot restore old bindings over that save. Before a save attempt, Back/Cancel retain their existing cancellation behavior, and leaving options without saving preserves files. A pending display confirmation must be resolved before Controller saving begins.

## Implementation boundary

- `Idas3PauseMenu.Controller.cs` is part of the existing pause menu, not a second application or binding engine. CONTROLS is tab 3 and WHEEL is tab 4. WHEEL uses secondary navigation within the existing panel; all eight Options categories remain visible and directionally reachable.
- `Idas3ControlBindings` owns checkpoint/restore for guided setup, explicit conflict rejection and one `EvaluateDriving` implementation used by saved gameplay and draft preview. Existing normalization, pedal rest/direction, paired-stick radial context and held-input/reconnect guards remain in place. Saved versions 1–3 are still accepted.
- `Idas3ControllerDevices` supports a nonpersistent selection preview with Apply/Cancel. Discovery and single-active-device selection remain the same; no save schema change is introduced.
- `Idas3GameOptions.ApplyWheelSettings` follows the existing scoped HUD transaction pattern, so applying FFB does not apply unrelated audio/display drafts.
- `Idas3SceneGame` supplies the test sample immediately after the normal physical-input Poll. It blocks tested inputs from menu actions, other managed menus and the submitted game packet. The existing menu/pause lifecycle still stops FFB. Native steering/physics and managed/native force calculation code are unchanged.

## Validation performed locally

57 portable checks compile the actual binding and game-option classes with small platform/serialization adapters. They cover controller/keyboard conflict rejection without unrelated changes, explicit clearing/rebinding, unsaved preservation, Setup checkpoint restoration, gameplay/preview parity, draft-versus-saved evaluation, custom wheel and reversed pedal normalization, capture/reconnect guards, keyboard recovery, old-format loading without writes, scoped FFB save and failed-apply rollback, combined saving, binding-file failure, device-save failure, FFB failure after earlier saves, retry, unrelated-option preservation and cancellation against the last saved state. The coordinator uses a simulated device writer in these portable checks; actual menu dispatch and device persistence are covered by explicit Unity checks that remain unrun. The adapters are not a Unity serializer or native player; their limits are intentional.

Run with .NET SDK 8:

```text
dotnet run --project Tests/ControllerFoundation/ControllerFoundation.csproj --configuration Release
```

C# syntax parsing also checks the source tree. Existing Unity menu/device smoke expectations were updated for separate CONTROLS and WHEEL categories and explicit occupied-binding rejection. The new `Idas3ControllerFoundationChecks.Run` is an explicit Unity editor check; it is not called during normal startup. It uses an isolated temporary preference directory and a synthetic gamepad filtered from physical-device discovery, and performs no FFB output.

## CONTROLS / WHEEL relocation acceptance

- Open each of the eight categories by pointer, keyboard/D-pad and wheel/pedal navigation. CONTROLS shows the familiar action table; WHEEL has Quick Setup, Overview, Bind Controls, Test Controls and Force Feedback. Check every bottom button, including WHEEL Back, focus borders and long driver names at target resolutions.
- Rebind or clear in CONTROLS; switch to WHEEL Overview/Draft and Bind Controls. The same edits must appear without a file write. Reverse the flow. Both categories identify saved active mode and draft mode; changing categories never changes modes. The mode switch remains in WHEEL. Multi-input uses per-action devices; the legacy device selector cannot secretly change it.
- Save Changes from either category saves shared bindings/device/FFB only; unrelated audio/display drafts stay pending. Discard restores the last saved shared state. Test cancellation before saving, an unfinished Setup when leaving WHEEL, and a completed review across categories. Preserve explicit conflicts, disconnected-slot clearing and nonpersistent device previews. Partial save messages remain available in both categories; exit remains guarded until retry or explicit discard.
- Test Controls blocks gameplay and stops when changing category. Use non-FFB wheels, pedals, shifters and button boxes as supported input sources; FFB capability is not an input eligibility requirement. Existing and multi-input mappings never run as two simultaneous gameplay evaluators.
- On the FFB page compare draft ENABLE with Saved enable and the actual backend status. Saved OFF with draft ON is pending, not an output defect. Check strength/output/inversion-only pending edits, menu output blocking, multi-input ownership blocking and unavailable backend status. This check requires no motor output.
